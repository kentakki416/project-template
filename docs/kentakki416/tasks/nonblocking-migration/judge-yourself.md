## Q1 — トランザクションの外で流す操作（`CREATE INDEX CONCURRENTLY` など）の定義をどこに持つか

- drizzle-kit はスキーマの index に `.concurrently()` を付けると `CREATE INDEX CONCURRENTLY` を生成するが、`db:migrate` は全体を 1 トランザクションで流すので、そのままでは失敗する（実機で確認）
- マイグレーションのフォルダに置いた余分なファイル（`online.sql`）は `db:migrate` に無視される。生成後に SQL から文を消しても、次の `db:generate` で差分は出ない（どちらも実機で確認）
- botchan-platform は b の方式で、対象は index だけ

| | 選択肢 | メリット | デメリット |
|---|---|---|---|
| a | マイグレーションのフォルダに `online.sql` を置く。`.concurrently()` を付けた index は `db:generate` の後処理が自動で移す **（推奨）** | index の定義がスキーマの 1 か所で済む / `migration.sql` と同じ場所・同じ順序で版管理される / `VALIDATE CONSTRAINT` も同じ経路に載る | 後処理・実行部・適用履歴のテーブルを自前で持つ / 「フォルダ内の余分なファイルを無視する」という drizzle-kit（RC）の挙動に依存し、版を上げるたびに確認が要る / 一度流した index が手で消されても戻さない |
| b | botchan-platform と同じ。スクリプト内の配列に index を登録し、生成された SQL から `CREATE INDEX` を手で削る | botchan-platform で動いている実績がある / 毎回あるべき姿を確かめるので、消された index も戻る / 履歴のテーブルが要らない | スキーマと配列の二重管理（カラムの食い違いは検出されない）/ SQL を手で削る作業が残る / index 以外（`VALIDATE CONSTRAINT`）は別の仕組みが要る |
| c | 仕組みは作らず、`docs/tech-stack/drizzle.md` の手動手順を補強する（本番 DB への接続手段、順序、失敗時の確認を書く） | コードが増えない | 本番 DB に手で SQL を流す経路を用意する必要がある / 実行を忘れてマージすると、通常の `CREATE INDEX` として流れて書き込みを止める / 無効な index の後始末が人任せ |

> **推奨は a。** 二重管理と手作業が無く、制約の検査も同じ経路で扱える。依存する挙動は確認済みで、版を上げるときの確認項目も決まっている。

## Q2 — バックフィル（既存の行のデータ移行）をどこに書き、どう起動するか

- 全行の `UPDATE` をマイグレーションに書くと、1 つの長いトランザクションになる。バッチに分けて、マイグレーションの外で流す必要がある
- deploy の one-shot タスクの待ちは 10 分で打ち切られる（`aws ecs wait tasks-stopped`）。バックフィルはこれを超えうる
- `apps/cron` は「1 回実行して exit する」タスクの枠組みを持ち、dev / min / prd にタスク定義がある。migration イメージは「Admin Create」のように、起動コマンドを差し替えて任意のスクリプトを流せる

| | 選択肢 | メリット | デメリット |
|---|---|---|---|
| a | `packages/db` にバッチ実行の仕組みと定義を置き、migration イメージを手動の workflow（「Postgres Backfill」）で起動する **（推奨）** | DB を変える作業が 1 つの package・1 つのイメージにまとまる / 起動の時刻と速度を人が決められる / `@repo/domain` の純粋関数は使える | workflow と、待ちの上限の改修が要る / app の Repository や service は使えない / 起動を忘れうる（次のリリースの制約の検査で気づく） |
| b | `apps/cron` のタスクとして書き、手動で起動する | 既存の枠組み（env の検証・logger・Repository・終了コード）がそのまま使える / 業務ロジックを使った移行が書きやすい | 定期実行のための app に、使い捨ての移行が混ざる / cron のタスクを手動で起動する workflow が別に要る / スキーマの変更（packages/db）と移行のコード（apps/cron）が離れる |
| c | a と同じ場所に書き、deploy の中で自動で起動する（完了は待たない） | 起動を忘れない | 負荷の高い時間帯に勝手に始まる / 失敗に気づきにくい / deploy のたびに「未完了のバックフィルがあるか」を判定する仕組みが要る |

> **推奨は a。** バックフィルはスキーマの変更と対で書いて対で消すもので、同じ package にあるほうが追いやすい。起動を忘れても、制約を付けるリリースが止まるので不正な状態にはならない。

## Q3 — 書き込みを止める DDL を、何で検出するか

- 今は、生成された SQL に素の `CREATE INDEX` があっても CI は止めない
- squawk は Postgres のマイグレーション用の linter で、npm（`squawk-cli`）で入る。`require-concurrent-index-creation`（同じトランザクションで作ったテーブルは対象外）、`constraint-missing-not-valid`、`adding-not-nullable-field`、`changing-column-type` などのルールと、`-- squawk-ignore <rule>` での除外がある（ドキュメントで確認。手元では動かしていない）
- drizzle-kit の生成する SQL をそのまま読めるかは未確認

| | 選択肢 | メリット | デメリット |
|---|---|---|---|
| a | squawk を CI で、PR が足した `migration.sql` にかける **（推奨）** | index・制約・NOT NULL・型の変更・default をまとめて検出できる / ルールの保守が要らない / 除外の理由が SQL に残る | 依存が 1 つ増える（Rust 製のバイナリを npm で配る形）/ 行数を知らないので、小さいテーブルでも除外のコメントが要る / 全行の `UPDATE` は検出できない見込みで、そこだけ自作が要る |
| b | 自作のスクリプト（正規表現で `CREATE INDEX` などを検出） | 依存が増えない / このリポジトリの規約（`online.sql` との対応など）に合わせて作れる | 対応する文を自分で増やし続ける / SQL を正しく解釈しないので見落としや誤検出が出る |
| c | 検出を入れず、レビューとドキュメントに任せる | 何も増えない | 気づくかどうかが人に依存する（今の状態のまま） |

> **推奨は a。** 止める DDL の種類は多く、自作では index 以外を取りこぼす。drizzle-kit の SQL を読めないことが分かった場合は b に切り替える。

## Q4 — トランザクションの外で流す操作が終わるまで、api の deploy を待つか

- 今の deploy は `build → migrate → api の切り替え` の順で、migrate の完了を待つ
- 行数の多いテーブルの index 作成は、数十分かかることがある
- 新しい api が unique index を前提にするコード（`ON CONFLICT` など）を含むと、index が無い間はエラーになる

| | 選択肢 | メリット | デメリット |
|---|---|---|---|
| a | 待つ。migrate ジョブの中で続けて流し、待ちの上限を 10 分から伸ばす **（推奨）** | api が切り替わった時点で index と制約が揃っている / ジョブの構成が今のまま / 失敗したら api は切り替わらない | index の作成が長いと、その間 deploy 全体が待つ（緊急の修正も待たされる） |
| b | 待たない。別ジョブにして api の deploy と並行で流す | deploy の時間が index の作成に引きずられない | index が無い状態で新しい api が動く時間ができる（unique index を前提にするコードは壊れる）/ 失敗しても api は切り替わっている / ジョブの依存関係が増える |

> **推奨は a。** 安全側で、構成も変わらない。deploy を待たせる長さが実際に問題になったら b を検討する（README の「MVP 対象外」に書いた）。
